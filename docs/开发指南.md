# 开发指南（接手开发必读）

> 面向接手开发者的"下一步怎么做"：开发环境、代码约定、常见扩展的完整步骤、
> 已知技术债清单。配合 `架构说明.md`（看懂现有代码）使用。
> 部署到服务器见 `部署指南.md`。

## 一、开发环境（Windows 为例）

```bash
uv sync                                   # 后端依赖
npm --prefix web install                  # 前端依赖（首次）
uv run python scripts/seed_demo.py        # 演示数据（幂等）
uv run python scripts/seed_roles.py       # 三角色账号（幂等）
uv run python run_dev.py                  # 后端 + worker（保持运行）
npm --prefix web run dev                  # 另开终端：前端热更新
```

日常循环：改代码 → 后端需重启 `run_dev.py`（未开 `--reload`）；前端 Vite 自动热更新。
测试命令见 `README.md`「常用命令」。

## 二、代码约定（动代码前先读）

| 约定 | 说明 |
|---|---|
| **错误处理** | 业务错误抛 `AppError(code, message, status)`（`app/core/errors.py`），统一信封返回；`code` 是稳定机器码，前端 `displayError(code, fallback)` 映射中文 |
| **权限校验** | 任何涉及项目的操作调 `require_project_permission(project_id, action, user, session)`；全局角色判断必须走 `app/identity/roles.py`（禁止直接 `user.role ==`） |
| **事务边界** | 路由层负责 `session.commit()`；service 层只 `flush()`。文件写入用 `_register_file_cleanup` 注册回滚补偿 |
| **不可变版本** | 永远不 UPDATE `DocumentVersion`（模型层有钩子拒绝）；改稿 = 上传新版本 |
| **mutating 工具** | Agent 工具若要改变状态：`ToolDefinition(mutating=True, ...)` + handler 内校验 `context.confirmed`；幂等键由前端生成 |
| **前端 API** | 一律走 `api/client.ts` 的方法（自动处理 token 注入、401 过期广播、错误信封），不直接 `fetch` |
| **测试伴随** | 每个改动配测试：后端放 `tests/{unit,integration}/`，前端放同目录 `.test.tsx`；E2E 在 `web/e2e/` |

## 三、常见扩展步骤

### 3.1 加一个后端 API 端点

1. 在对应模块的 `router.py` 加路由函数（`Annotated[User, Depends(get_current_user)]` 拿当前用户）
2. 业务逻辑放同模块 `service.py`（先做权限校验，再操作）
3. 需要新请求/响应模型 → 加到模块 `schemas.py`
4. 前端：`api/client.ts` 加方法 → 对应 `features/*` 组件调用
5. 测试：`tests/integration/test_<模块>.py` 用 `TestClient` 覆盖成功 + 无权限 403 两条路径
6. 跑 `uv run pytest tests/integration -q` 与 `npx tsc --noEmit`

### 3.2 加一个 Agent 质量工具

1. `app/quality/tools.py`：定义 `XxxInput(BaseModel)`（`extra="forbid"`）+ handler + 注册 `ToolDefinition`
2. `app/quality/prompts.py`：`CAPABILITY_PROMPTS` 加一条能力描述，**并递增 `PROMPT_VERSION`**
   （`tests/unit/test_audit_prompt.py` 会断言能力常量必须出现在 prompt 里）
3. 若工具产出要显示给前端：在 `ToolTrace` 结果里带结构化字段；前端 `AgentWorkspace`/`ToolTrace.tsx` 按需渲染
4. 测试：`tests/unit/test_<工具>.py` —— 输入校验、越权拒绝、正确返回三类用例

### 3.3 加一个后台任务类型

1. 实现 `JobHandler` 子类（`app/jobs/runner.py`）：`run(payload: dict) -> dict`
   - payload 校验用 Pydantic 模型（参考 `IngestionJobPayload`）
   - 可重试错误抛 `RetryableJobError`
2. `run_worker.py::build_registry` 注册该 handler
3. 生产端：在触发点调用 `jobs.service.enqueue(session, "任务名", payload, owner_id, idempotency_key)`
   —— 必须在业务事务内调用（提交失败一起回滚）
4. 幂等键设计：用业务实体 ID（如 `f"knowledge.ingest:{version_id}"`）
5. 测试参考 `tests/integration/test_ingestion_queue.py`（入队幂等 + worker 消费 + 永久失败三例）

### 3.4 改数据库 schema（加表/加列）

1. 改 SQLAlchemy 模型（`app/*/models.py`）
2. 生成迁移：`uv run alembic revision -m "描述"`（手写 `upgrade()`/`downgrade()`；本项目不用 autogenerate——
   `alembic check` 有已知噪声，见 `运维手册.md` §三）
3. **不要改已发布的历史迁移文件**（`0001`-`0009` 已在使用）
4. FTS 相关：虚拟表 `knowledge_chunks_fts` 不在 `Base.metadata`，集成测试需手动建
   （参考 `tests/integration/test_ingestion_queue.py::make_env`）
5. 验证：`uv run alembic upgrade head` 起新库 + 跑全量测试

### 3.5 前端加一个功能页面

1. `web/src/features/<功能>/` 新建组件（参考 `features/comparison/` 的完整结构：组件 + 测试 + 调 `api`）
2. 路由：`App.tsx` 的导航数组与 `view` 分支（hash 路由，无 router 库）
3. 权限显隐：从 `web/src/app/roles.ts` 取判断（多角色接缝）

## 五、已知技术债 / 取舍（避免踩坑）

- **SQLite 单写者**：单实例设计。多实例/高并发需先迁 PostgreSQL（替换顺序：SQLite→PG、worker→专业队列、FastEmbed→专用检索）
- **API 侧用 IMMEDIATE 事务（2026-09-14 修复）**：`create_database_engine(..., immediate_transactions=True)`
  只在 API 侧开启（`app/main.py`）：写路径都是「先读校验、再写更新」，WAL 下这种延迟事务
  只要在读写之间有别的连接提交，就会立刻抛 `SQLITE_BUSY_SNAPSHOT`（`busy_timeout` 对写升级无效），
  表现为随机 500 / 提交卡住。worker 侧保持延迟事务 + 既有重试（事务可能较长，不宜抢先占写锁）。
  `busy_timeout` 已提到 15s，因此与索引抢锁时**写操作会排队等待**，不要把「等待」误判为卡死。
- **语义检索硬失败**：向量模型缺失时检索报错而非静默降级（有意设计）；离线环境必须预取模型或 `EMBEDDING_ENABLED=false`
- **中文关键词检索：单字索引 + bigram 兜底（2026-09-15 修复）**：`ingestion._fts_text` 把每个汉字
  单独成词，查询先用单字 AND 保精度，**零命中时**退回「相邻二字短语」OR 保召回
  （`search._fts_query_any`，靠 FTS5 短语查询实现真正的 bigram 匹配）。若始终用 AND，
  约束强度与「输入了多少个字」成正比，「差旅补助」能命中而「差旅补助标准」返回空。
  拉丁词是整词 token，AND 本就是预期语义，不参与降级。根治方案是换 trigram/分词器并重建索引。
- **语义对比是"诚实降级"设计**：离线/异常时如实标注 `engine=heuristic/difflib`，不要"优化"成冒充模型
- **`alembic check` 有噪声**：不能作为 CI 门槛（`运维手册.md` §三列了具体差异）
- **文件事务补偿**：`documents/service.py` 的 `after_commit/after_soft_rollback` 钩子较微妙，改动 `create_version` 前先读注释
- **E2E 环境自管理**：`npm run test:e2e` 会自起隔离栈（独立端口+临时库+worker 进程），不要手动改端口/复用开发库

## 六、开发与验收流程（建议）

1. 接手第一周：跑通 `README.md` 启动 + 三套测试 + 用三角色账号走一遍 `使用手册.md` 演示脚本
2. 每次改动：按 §二约定 + 伴随测试；提交前 `ruff` + `pytest` + `tsc` + `vitest`
3. 功能完成：E2E 补一条（参考现有 5 个 spec）
4. 合并到 `main`：CI（ruff + pytest / tsc + vitest）与 E2E 两条 workflow 全绿
